# Шаги для Claude Code: генерация robustness-датасета (мусорный/нерелевантный ввод)

Контекст: дополняет `claude_code_steps.md` (Шаг 4 — Layer 0). Это отдельная категория, отличная от `out-of-scope` (связный текст не по теме) и `no-data` (по теме, но без деталей). Здесь цель — проверить устойчивость системы (и intent-классификатора, и самого `parseInvoiceFromText`) к вводу, который в принципе не должен был попасть в эту функцию.

Общий флаг для всех примеров ниже: `is_invoice_request: false`, `input_type: <категория>` (см. ниже). `ground_truth: null`.

## Категория 1 — Irrelevant function call (не туда обратились)
Пользователь находится в приложении, но хотел вызвать другую функцию — не парсинг инвойса. Примеры: просьба написать письмо-напоминание об оплате (это отдельная функция `generateReminderEmail`), просьба дать саммари по дашборду (`getDashboardSummary`), общий вопрос про то, как пользоваться приложением, жалоба на баг.
- Генерация: LLM, промпт — "напиши короткое сообщение пользователя приложения для выставления счетов, который хочет [конкретное другое действие], а не создать инвойс"
- Важно: тексты должны звучать правдоподобно в контексте именно этого приложения (billing/invoicing SaaS), не абстрактный "не по теме" текст — это отличает категорию от `out-of-scope`
- `input_type: wrong_function`
- ~20-30 примеров

## Категория 2 — Spam
Повторяющийся, рекламный или бессмысленно-навязчивый текст.
- Генерация: программно (без LLM) — шаблоны с повторами слов/фраз, случайные рекламные фразы, повторяющиеся спецсимволы (`"BUY NOW BUY NOW BUY NOW..."`, `"!!!!!!!!!!!!!!!!"`, случайные URL-подобные строки)
- `input_type: spam`
- ~15-20 примеров

## Категория 3 — HTML / код / разметка вместо текста
Симулирует случайную вставку не того содержимого (скопировал не то из буфера обмена).
- Генерация: программно — взять реальные фрагменты HTML/JSON/XML/кода (можно use случайные сниппеты из открытых источников или сгенерировать шаблонно: `<div class="...">...</div>`, JSON-объекты не по нашей схеме, куски Python/JS кода)
- `input_type: markup_or_code`
- ~15-20 примеров

## Категория 4 — Случайный набор символов (gibberish)
- Генерация: программно — случайные последовательности букв/цифр/спецсимволов разной длины, включая: пустую строку, строку только из пробелов, очень короткий ввод (1-2 символа), очень длинный бессмысленный ввод (стресс на длину)
- `input_type: gibberish`
- ~15-20 примеров

## Выход
Сохранить как `robustness_dataset.jsonl`, объединить с `layer0_dataset.jsonl` на этапе финальной сборки (`claude_code_steps.md`, Шаг 6).

Структура записи:
```json
{
  "id": "...",
  "raw_text": "...",
  "ground_truth": null,
  "is_invoice_request": false,
  "input_type": "wrong_function|spam|markup_or_code|gibberish",
  "generation_method": "llm|programmatic",
  "generation_prompt_version": "v1|n/a"
}
```

## Зачем это отдельно от out-of-scope/no-data
- `out-of-scope` / `no-data` тестируют **семантическое понимание intent** — умеет ли модель отличить релевантный запрос от нерелевантного, но осмысленного
- Этот robustness-слой тестирует **устойчивость самого пайплайна** к вводу, которого в проде вообще не должно было бы дойти до LLM в таком виде — особенно важно, учитывая, что `parseInvoiceFromText` использует хрупкий `JSON.parse` без валидации (см. `project_brief.md`, "Known baseline weaknesses") — здесь легко получить необработанное исключение, а не просто неверный ответ
- В отчёте это даёт отдельную метрику: **crash/exception rate on malformed input** — отдельно от error rate на нормальных данных

## Метрика для Layer 0 (уточнение)
При анализе результатов разделять:
- Ошибки на `wrong_function`/`out-of-scope`/`no-data` — это качество intent-классификации (soft failure, модель отвечает, но неверно)
- Ошибки на `spam`/`markup_or_code`/`gibberish` — это отказоустойчивость системы (hard failure, может быть exception/crash, не просто неверный JSON)
