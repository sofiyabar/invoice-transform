# Data Map

## 1. Общая картина

Система превращает текст без структуры в структурированный инвойс и оценивает качество
этого превращения. Оценка идёт в три этапа, один за другим: **сначала** понять, просят ли
вообще инвойс; **затем** — хватает ли для него данных; **в конце** — извлечь поля и сравнить
с правильным ответом. Результат каждого этапа — свой набор метрик. Все метрики одного
прогона собираются в один файл (`eval_runs/*_metrics.json`), и этот файл целиком показывается
на дашборде.

Дальше документ раскрывает эту картину по уровням: сначала входные данные (раздел 2), затем
каждый этап обработки со своими метриками (раздел 3), затем как это всё упаковано в один
файл (раздел 4) и как файл попадает на экран (раздел 5).

## 2. Входные данные

### 2.1 Тестовые записи

Система проверяется на 600 **записях** (`data/synthetic/eval_dataset.jsonl`). Запись — это
входной текст плюс заранее известный правильный ответ по нему. Записи различаются по двум
признакам:

- **сегмент** — насколько сложен текст: `clean` (чистый, без помех), `noisy` (с опечатками и
  лишними деталями), `edge_case` (нетипичный пограничный случай)
- **тип документа** — форма текста: `email`, `chat` (короткое неформальное сообщение),
  `receipt_ocr` (распознанный чек)

Часть записей — не про инвойс вообще (мусор, спам) или содержит недостаточно данных для
инвойса — это отдельно проверяется на этапе 3.1–3.2 ниже. Полное описание полей записи —
`data/synthetic/dataset_manifest.md`.

### 2.2 Конфиги

**Конфиг** — значение, которое нельзя вычислить из данных и задаётся вручную: во сколько
долларов оценивается ошибка в поле, час ручной проверки, штраф за нарушение срока ответа
(`config/severity_weights.yaml`, `config/business_assumptions.yaml`). Нужны только для этапа
3.6 (деньги) и пока не заполнены реальными числами.

## 3. Этапы обработки и их метрики

Каждый этап ниже описан по одной схеме: что система делает → как это измеряется.

### 3.1 Понимание намерения

Система решает: этот текст вообще просьба сделать инвойс? Да/нет.

| Метрика | Значение | Что показывает |
|---|---|---|
| `accuracy` | доля 0–1 | как часто решение верное |
| `fp_rate` | доля 0–1 | как часто система принимает мусорный текст за просьбу сделать инвойс — дорогая ошибка: инвойс уходит клиенту из ничего |
| `fn_rate` | доля 0–1 | как часто система отклоняет настоящую просьбу — дешёвая ошибка: пользователь просто повторяет запрос |

### 3.2 Проверка достаточности данных

Если шаг 3.1 сказал "да" — система решает: данных хватает, чтобы построить инвойс?
Три варианта: нет данных / частично / достаточно.

| Метрика | Значение | Что показывает |
|---|---|---|
| `accuracy` | доля 0–1 | как часто верно определён уровень |
| `missed_shortage_rate` | доля 0–1 | как часто система решает, что данных достаточно, хотя не хватает — опасная ошибка: инвойс уйдёт с дырой |
| `asked_unnecessarily_rate` | доля 0–1 | как часто система просит уточнить данные, хотя их и так хватало — лишнее неудобство для пользователя |
| `missing_fields` (precision/recall/f1) | доля 0–1 | насколько точно система называет, каких именно полей не хватает |

### 3.3 Извлечение полей

Если данных достаточно — система извлекает поля инвойса из текста. Результат называется
**ответом системы (prediction)**. Prediction сравнивается с **правильным ответом (ground
truth)** — значениями полей, заданными вручную при создании записи. Результат сравнения по
каждому полю — **оценка (score)**: 1, если совпало, 0, если нет.

| Метрика | Значение | Что показывает |
|---|---|---|
| `field_scores.<поле>.error_rate` | доля 0–1 | как часто конкретное поле (имя клиента, email, адрес, позиции) извлечено неверно |
| `parse_failure_rate` | доля 0–1 | как часто ответ системы вообще нельзя прочитать как результат (сломанный формат) |

### 3.4 Итог по документу

Оценки по отдельным полям одной записи сворачиваются в один вывод: готов ли весь документ
целиком. Из полей выделены **критичные**: имя клиента (`clientName`) и позиции счёта
(`items`) — ошибка в них делает документ непригодным к отправке без проверки человеком; email
и адрес не критичны, их можно дополнить вручную позже.

| Метрика | Значение | Что показывает |
|---|---|---|
| `resolution_rate` | доля 0–1 | доля документов, где все критичные поля верны — готовы к отправке без проверки человеком |
| `critical_error_rate` | доля 0–1 | доля документов с ошибкой хотя бы в одном критичном поле; всегда `1 − resolution_rate` |
| `resolution_rate_ci` | диапазон | **доверительный интервал** — диапазон, в который с высокой вероятностью попадает истинное значение resolution_rate; нужен, потому что метрика посчитана на ограниченной выборке |
| `by_segment`, `by_doc_type` | те же метрики по группам | где именно система справляется хуже — по сегменту или типу документа (раздел 2.1); реальна ли разница показывает **p-value** — вероятность, что разница между группами случайна; если меньше 0.05, разницу считают реальной |

### 3.5 Симуляция поведения в проде

Дополнительные метрики о том, как система вела бы себя в реальной эксплуатации — не про
точность извлечения.

| Метрика | Значение | Что показывает |
|---|---|---|
| `technical_error_rate` | доля 0–1 | как часто сам вызов системы падает технически |
| `latency` (p50/p95/mean) | миллисекунды | время обработки одного документа — здесь это оценка, реальных замеров пока нет |
| `csat_proxy.thumbs_down_rate` | доля 0–1 | приблизительная доля недовольных пользователей, посчитанная от critical_error_rate — не опрос реальных людей |

Такие значения помечены в данных полем `is_stub` или `is_estimate`, чтобы их нельзя было
спутать с измеренными.

### 3.6 Деньги

Не реализовано. Должно переводить метрики выше в стоимость ошибок и экономию, используя
конфиги из раздела 2.2. Формулы — `.claude/.skills/project_brief.md`, раздел Layer 6.

## 4. Файл одного прогона

Всё из раздела 3 собирается в один файл `eval_runs/*_metrics.json`. Его пишет целиком
`evals/runner.py` — ничего в нём не меняется другими частями системы.

```
metrics_dict
├── run_id                когда прогон запущен
├── config                 как именно прогон был запущен (сколько записей, какая модель)
├── layer0                  результаты 3.1–3.2 | пусто, если не считалось
├── layer1                  результаты 3.3
│   └── records                результат по каждой отдельной записи
├── layer2                  результаты 3.4 | пусто
├── layer3                  всегда пусто — цифры внутри layer2
├── layer4                  результаты 3.5 | пусто
├── layer5                  всегда пусто — цифры внутри layer2
└── layer6                  всегда пусто — раздел 3.6 не реализован
```

## 5. Дашборд

Дашборд читает последний файл из раздела 4 и показывает по одной вкладке на каждый этап
из раздела 3.

| Вкладка | Берёт из файла | На какой вопрос отвечает |
|---|---|---|
| Layer 0 | `layer0` | Правильно ли система понимает намерение и хватает ли данных? (3.1–3.2) |
| Layer 1 | `layer1` | На каких полях система чаще всего ошибается? (3.3) |
| Layer 2 | `layer2` | Сколько инвойсов готовы к отправке, и где хуже всего? (3.4) |
| Layer 3 | — | Пусто: цифры на вкладке Layer 2 |
| Layer 4 | `layer4` | Как быстро это работает и понравится ли пользователям? (3.5) |
| Layer 5 | — | Пусто: цифры на вкладке Layer 2 |
| Layer 6 | — | Сколько это стоит/экономит в деньгах? — не реализовано (3.6) |
